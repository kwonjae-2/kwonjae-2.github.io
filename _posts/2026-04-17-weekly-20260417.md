#### 1. [13시간 만에 €54,000 과금 폭증: API 제한 없는 Firebase 브라우저 키로 Gemini API 호출 발생](https://news.hada.io/topic?id=28635)

#### 2. [HTTP desync in Discord's media proxy: Spying on a whole platform](https://tmctmt.com/posts/http-desync-in-discord/)
**출처:** lobsters | **날짜:** 2026-04-17

이 글(및 댓글)은 Discord 미디어 프록시에서 발생한 HTTP desync(요청/응답 불일치) 취약점이 어떻게 프록시-업스트림 간 파싱 차이를 이용해 요청을 스머글링하고, 결과적으로 다른 사용자의 트래픽을 엿보는 수준의 영향으로 이어질 수 있는지 다룹니다. 개발자는 프록시/로드밸런서/캐시가 섞인 환경에서 HTTP 경계(메시지 길이, 헤더 해석, 커넥션 재사용)가 보안 경계가 될 수 있음을 배우고, 이를 테스트·완화하는 실무 체크리스트를 얻습니다.

**핵심 포인트:**
- 프록시/업스트림 전 구간에서 HTTP 파서를 ‘동일하게’ 맞추세요: HTTP/1.1을 쓴다면 Content-Length vs Transfer-Encoding, 다중 Content-Length, 비정상 공백/대소문자, obs-fold 등 모호한 케이스를 명시적으로 거부하고, 가능한 한 엣지에서 HTTP/2(또는 H2C 내부)로 승격해 메시지 경계 모호성을 줄이세요.
- 커넥션 재사용과 격리를 점검하세요: 공유 업스트림 커넥션(keep-alive 풀링)이 사용자 간 응답 혼선을 만들지 않도록 요청 단위 라우팅/키잉을 보장하고, 의심스러운 입력(TE+CL, 중복 CL 등)이 감지되면 해당 커넥션을 즉시 드롭하며, 프록시 계층마다 timeouts/body size 제한을 일관되게 적용하세요.
- 재현 가능한 보안 테스트를 CI에 넣으세요: h2c/h1 변환, CDN/리버스프록시/앱서버 조합에서 request smuggling/desync 페이로드를 퍼징(예: TE+CL, chunked 종료 변형, 파이프라이닝)하고, 로그/트레이싱에 ‘요청 경계 식별자(요청 길이, 파싱 결과, 업스트림 바이트 수)’를 남겨 조기 탐지와 회귀 방지를 하세요.

#### 2. [HTTP desync in Discord's media proxy: Spying on a whole platform](https://tmctmt.com/posts/http-desync-in-discord/)
**Source:** lobsters | **Date:** 2026-04-17

This article (and its comments) discusses an HTTP desync (request/response mismatch) issue in Discord’s media proxy, showing how parsing differences between a proxy and its upstream can enable request smuggling and, at worst, cross-user traffic exposure. Developers learn why HTTP message boundaries (length, header parsing, connection reuse) become a security boundary in multi-proxy/caching setups, plus practical ways to test for and mitigate these failures.

**Key Points:**
- Align HTTP parsing across proxy and upstream: if you must use HTTP/1.1, explicitly reject ambiguous cases (Content-Length vs Transfer-Encoding, multiple Content-Length, odd whitespace/casing, obs-fold, etc.), and prefer upgrading to HTTP/2 at the edge to reduce message-boundary ambiguity.
- Audit connection reuse and isolation: ensure shared upstream keep-alive pools cannot mix responses across users, drop the connection immediately when suspicious inputs (TE+CL, duplicate CL) are seen, and apply consistent timeouts and body-size limits at every proxy layer.
- Put reproducible security tests in CI: fuzz request-smuggling/desync payloads across your CDN/reverse-proxy/app-server chain (including h2/h1 transformations), and log/trace request-boundary signals (declared length, parse decisions, upstream bytes) to detect early and prevent regressions.
