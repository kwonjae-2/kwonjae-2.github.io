#### 1. [AUR Packages Compromised with Infostealer and Rootkit](https://discourse.ifin.network/t/400-aur-packages-compromised-with-infostealer-and-rootkit/577)
**출처:** hackernews | **날짜:** 2026-06-12

AUR(Arch User Repository) 패키지에 인포스틸러 및 루트킷이 포함된 형태로 공급망이 침해될 수 있음을 보여주는 사례로, 개발자는 ‘신뢰하는 패키지’라도 설치·업데이트 과정에서 악성 행위가 섞일 수 있음을 배웁니다. 특히 PKGBUILD/설치 스크립트가 네트워크에서 추가 페이로드를 내려받거나 권한 상승/지속성 확보를 시도할 수 있어, 패키지 검증과 최소 권한 설치, 감사 절차의 중요성을 얻습니다.

**핵심 포인트:**
- AUR 설치 전 PKGBUILD와 .install 스크립트를 반드시 검토하고, 원격 다운로드(curl/wget), 난독화된 파이프 실행(bash -c), 의심스러운 post-install 훅, 권한 변경(setuid/커널 모듈/서비스 등록) 여부를 체크리스트로 확인하세요.
- 패키지 설치/빌드는 격리 환경(컨테이너/VM)에서 수행하고, 가능한 한 root 권한을 피하며(특히 makepkg의 비-root 원칙), sudo 사용을 최소화하고 허용 범위를 명시적으로 제한하세요.
- 내부에서 사용하는 AUR/외부 패키지는 버전 고정과 허용 목록(allowlist) 기반으로 운영하고, 해시/서명 검증(가능한 경우), 아티팩트 미러링, 설치 후 무결성·이상 징후 모니터링(새 서비스/크론/커널 모듈/의심 네트워크 연결)을 자동화하세요.

#### 3. [AI agent bankrupted their operator while trying to scan DN42](https://lantian.pub/en/article/fun/ai-agent-bankrupted-their-operator-scan-dn42lantian.lantian/)
**출처:** hackernews | **날짜:** 2026-06-12

AI 에이전트가 네트워크 스캔 작업(DN42 관련)을 수행하는 과정에서 비용 통제 없이 외부 리소스를 과도하게 사용해 운영자 계정에 큰 금전적 피해를 낸 사례를 다룹니다. 개발자는 에이전트/자동화 작업이 ‘의도한 목표’만큼이나 ‘비용·권한·안전 한계’를 반드시 갖춰야 하며, 관측(로그/메트릭)과 가드레일이 없으면 작은 실험도 장애나 요금 폭탄으로 이어질 수 있음을 얻습니다.

**핵심 포인트:**
- 에이전트 실행에 예산 한도(일/시간 단위 캡), 쿼터, 자동 종료 조건(최대 요청 수/최대 실행 시간/최대 동시성)을 강제하고, 결제/클라우드 계정에는 알림+차단(soft/hard limit)을 함께 설정하세요.
- 권한을 최소화(least privilege)하고 위험한 작업(스캔, 대량 요청, 외부 API 호출)은 정책 기반 허가(allowlist 도메인/포트/대상 범위, 승인 워크플로, 휴먼 인 더 루프) 없이는 실행되지 않도록 분리하세요.
- 관측 가능성을 기본값으로 두고(요청 수, 오류율, 대상 수, 토큰/비용, 네트워크 egress), 이상 징후 감지 시 자동 페일세이프(즉시 중단, 롤백, 레이트 리밋 강화)로 전환되도록 런북과 테스트(시뮬레이션/드라이런)를 마련하세요.

#### 4. [WASI 0.3.0 Released](https://github.com/WebAssembly/WASI/releases/tag/v0.3.0)
**출처:** hackernews | **날짜:** 2026-06-12

WASI 0.3.0 릴리스(및 HN 댓글)는 WebAssembly 모듈이 OS 기능(파일, 네트워크, 시간 등)에 접근하는 표준 인터페이스가 어떻게 진화하는지와, 실제 개발·배포에서 어떤 호환성/이행 비용이 생기는지를 다룹니다. 개발자는 새 버전에서 달라진 API/툴체인/런타임 지원 상황을 파악하고, 샌드박싱 기반의 이식 가능한 컴포넌트 배포 전략을 더 안정적으로 설계하는 데 도움을 얻습니다.

**핵심 포인트:**
- 현재 사용하는 런타임(Wasmtime/Wasmer/WAMR 등)과 툴체인(언어 SDK)이 WASI 0.3.0을 어느 수준까지 지원하는지 매트릭스를 만들고, CI에서 `wasm` 타깃 빌드를 분리해 호환성 회귀를 조기에 잡으세요.
- 애플리케이션의 시스템 의존 지점(파일 I/O, 소켓, 환경변수, 시간/난수 등)을 목록화하고, WASI 인터페이스 경계(어댑터/포트)로 캡슐화해 버전 업그레이드 시 변경 범위를 최소화하세요.
- 배포 시에는 권한 기반(capability-based) 설정을 기본으로 하고, 필요한 디렉터리/네트워크만 명시적으로 열어주는 실행 설정을 템플릿화하여(예: 런타임 옵션/매니페스트) 개발·운영 환경에서 동일한 보안 모델을 재현하세요.

**핵심 포인트:**
- 프롬프트에 ‘제약 조건’을 명시하세요: 디자인 시스템/컴포넌트 라이브러리(예: MUI, Tailwind), 상태 관리 방식, 접근성(ARIA), 타입스크립트 사용 여부, 폴더 구조와 코딩 규칙(네이밍/포맷)을 구체적으로 요구합니다.

- ‘슬로피함’의 정의를 체크리스트로 표준화하고 반복 피드백을 주입하세요: 불필요한 div/중복 스타일/인라인 스타일/매직 넘버/비일관 네이밍/aria 누락 등을 항목화하고, 리뷰 코멘트·리팩터링 예시를 다음 프롬프트/컨텍스트에 반영합니다.

#### 8. [Encrypted Spaces An architecture for collaborative applications](https://encryptedspaces.org/)
**출처:** hackernews | **날짜:** 2026-06-12

이 글(댓글 중심)은 협업 애플리케이션에서 ‘Encrypted Spaces’ 같은 구조를 통해 데이터가 서버에 평문으로 노출되지 않도록 하면서도 실시간 협업을 가능하게 만드는 설계 아이디어를 다룹니다. 개발자는 키 관리/권한 모델, 클라이언트 중심 암호화, 그리고 충돌 해결(CRDT/OT) 같은 동기화 레이어를 어떻게 결합할지에 대한 트레이드오프(검색/인덱싱, 운영/복구, 성능)를 배울 수 있습니다.

**핵심 포인트:**
- 권한/공유 모델을 먼저 정의하라: 스페이스(워크스페이스) 단위 키, 사용자/그룹 멤버십 변경(초대/추방) 시 키 회전, 디바이스 추가 시 안전한 키 에스크로/재암호화 흐름을 설계하고 위협 모델(서버/클라이언트 침해)을 문서화한다.
- 암호화 경계를 명확히 하라: 클라이언트에서 콘텐츠를 암호화하고 서버는 불투명한 블롭+메타데이터만 다루도록 하며, 어떤 메타데이터(문서 ID/타임스탬프/접근 제어)까지 노출할지 최소화하고 감사 로그/재현 가능한 암호화(버전 태깅)를 포함한다.
- 협업 동기화는 ‘암호화된 상태’와 분리해 설계하라: CRDT/OT 이벤트를 암호화하기 전/후 어느 단계에서 적용할지 결정하고, 오프라인 편집/재접속 시 재동기화, 키 변경 시 과거 이벤트 재처리, 대역폭 최적화(델타/스냅샷)를 테스트 케이스로 고정한다.

#### 9. [Kimi K2.7-Code: open-source coding model with better token efficiency](https://huggingface.co/moonshotai/Kimi-K2.7-Code)
