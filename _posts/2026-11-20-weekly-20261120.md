#### 1. [Postgres 19 REPACK: 더 빠른 내장 테이블 비대화 정리](https://news.hada.io/topic?id=37536&utm_source=geeknews&utm_medium=rss&utm_campaign=news)
**출처:** geeknews | **날짜:** 2026-11-20

Postgres 19는 확장 없이 테이블 비대화를 정리하고 디스크 공간을 OS에 반환하는 새 SQL 명령 REPACK을 도입합니다. CONCURRENTLY 옵션을 통해 대부분의 시간 동안 읽기/쓰기를 유지하면서 온라인으로 테이블을 재구축할 수 있고, VACUUM과 VACUUM FULL 대비 잠금·운영 영향의 트레이드오프를 이해하게 됩니다.

**핵심 포인트:**
- 비대화로 실제 디스크를 줄여야 할 때는 VACUUM(내부 재사용)과 달리 OS로 공간을 돌려주는 REPACK을 고려하고, 운영 중단을 최소화하려면 REPACK CONCURRENTLY를 우선 검토하세요.
- REPACK은 마지막 파일 교체 시점에만 짧은 잠금이 필요하므로, 트래픽이 낮은 시간대에 실행하고 잠금 대기/쿼리 지연을 모니터링하는 실행 절차(런북)를 준비하세요.
- 테이블 재작성 경로를 통제하려면 USING INDEX(가능한 경우) 같은 옵션을 활용하고, 실행 전후로 테이블/인덱스 크기, bloat 추정치, 쿼리 성능(특히 대형 테이블 스캔/업데이트)을 측정해 효과를 검증하세요.

#### 2. [Jujutsu 입문: Git 사용자에게 익숙하면서도 다른 버전 관리 방식](https://news.hada.io/topic?id=37531&utm_source=geeknews&utm_medium=rss&utm_campaign=news)
**출처:** geeknews | **날짜:** 2026-11-20

이 글은 Git 저장소 위에서 Git과 함께 사용할 수 있는 버전 관리 도구 Jujutsu(jj)를 소개하며, 커밋 그래프 중심 워크플로(자동 스냅샷, 자동 리베이스, 강력한 실행 취소)가 개발 생산성을 어떻게 높이는지 설명합니다. 스테이징 영역 없이 작업 사본 자체를 커밋으로 관리하고, 커밋 ID가 바뀌어도 change ID로 논리적 변경을 추적하며, 충돌을 ‘기록된 상태’로 남긴 채 작업을 계속할 수 있는 점을 개발자가 얻어갈 수 있습니다.

**핵심 포인트:**
- 개인 브랜치/피처 작업에서 `jj`로 자동 스냅샷 기반 흐름을 시도해 보세요: 파일을 편집한 뒤 `jj` 명령으로 상태를 바로 기록하고, 스테이징(add) 없이 작은 변경 단위로 커밋 그래프를 쌓는 습관을 만듭니다.
- 리라이트(과거 커밋 수정)와 히스토리 정리에 jj의 자동 리베이스 모델을 활용하세요: 이전 커밋을 고치면 후손 커밋이 자동으로 재배치되므로, PR 올리기 전 커밋 메시지/내용 정리를 더 자주·가볍게 수행할 수 있습니다.
- 충돌 처리 전략을 바꾸세요: 충돌이 나면 즉시 다 해결하려고 멈추기보다, 충돌 상태를 기록한 채 다른 작업을 진행하고 나중에 한 번에 해결하는 워크플로를 팀/개인 작업에 적용해 보세요.

- 아키텍트 업무의 산출물을 ‘가볍게’ 표준화하세요: 1~2페이지 아키텍처 브리프(문제/목표/제약, 대안, 트레이드오프, 위험, 관측 지표) + ADR 템플릿으로 결정 기록을 남겨 팀의 재논의를 줄입니다.
- 코딩 시간과 조율 시간을 보호하는 운영 규칙을 만드세요: 주간 ‘메이커 타임’ 블록, 회의 상한선, 리뷰 SLA(예: 48시간), 그리고 “당신의 역할에서 성공이 뭔가?”(예: 리드타임/가용성/비용 목표)를 분기별로 재확인합니다.

#### 4. [코드 작성을 멈추면 코드 리뷰 실력도 떨어진다](https://news.hada.io/topic?id=37534&utm_source=geeknews&utm_medium=rss&utm_campaign=news)

이 글은 코드를 직접 작성하지 않고 지시·리뷰만 하는 방식으로는 개발 전문성과 코드 리뷰 역량을 지속적으로 유지·향상시키기 어렵다고 강조한다. AI가 만든 코드의 단기 품질보다 중요한 쟁점은 ‘직접 구현하며 문제를 푸는 연습’을 하는 개발자와 그렇지 않은 개발자 사이에서 숙련도가 어떻게 벌어지는지다. 좋은 코드의 특성과 변경하기 쉬운 구조를 이해하려면, 생성된 코드를 보는 것만이 아니라 직접 설계·구현·디버깅하는 경험이 필요하다는 메시지를 준다.

**핵심 포인트:**
- 매주 ‘손코딩 시간’을 캘린더에 고정(예: 2~4시간)하고, 실제 제품 코드에서 작은 기능/버그 수정 1개를 끝까지 구현·테스트·배포까지 해보며 감각을 유지한다.
- AI를 쓰더라도 “내가 설계 → AI는 초안” 원칙을 세운다: 먼저 요구사항/에지케이스/테스트 전략을 작성한 뒤, 생성된 코드에 대해 불변식·복잡도·에러 처리·리팩터링 포인트를 체크리스트로 검증한다.
- 리뷰 역량을 ‘리뷰만’으로 키우려 하지 말고, 리뷰에서 발견한 이슈를 직접 고쳐보는 루프를 만든다(예: 매 스프린트 1건은 리뷰 코멘트를 내가 직접 패치로 반영하고 회고).

#### 5. [언어 모델은 자신의 가중치를 직접 다시 쓸 수 있다](https://news.hada.io/topic?id=37540&utm_source=geeknews&utm_medium=rss&utm_campaign=news)

Qwen3.5 27B는 실패 사례와 채점된 답변, 실행 도구를 활용해 스스로 오류 원인을 진단하고, 그래디언트 계산이나 추가 학습 없이 모델 가중치를 직접 수정해 미공개 문제 정확도를 6.6%p 개선했습니다. 개발자는 이 ‘self-rewriting’ 접근을 통해 배포 후에도 프롬프트/추가 추론비용 없이 모델 자체를 개선하고, 수정안은 별도 검증(연습 문제)으로 안전성을 확인할 수 있다는 점을 배웁니다.

**핵심 포인트:**

- 수정안을 바로 배포하지 말고, 제출 전 ‘연습 문제(holdout) 스위트’로 정확도/회귀를 검증하고, 기준 미달이면 수정안을 철회하는 게이트(roll-back)를 두세요.
- 가중치 수정이 누적될 때 위험이 커질 수 있으니 세션별로 변경을 버전 관리(체크포인트, diff, 메타데이터)하고, 필요 시 ‘기본 가중치에서 재시작’하거나 안정적인 수정만 선택적으로 병합하는 운영 정책을 마련하세요.

#### 1. [Postgres 19 REPACK: 더 빠른 내장 테이블 비대화 정리](https://news.hada.io/topic?id=37536&utm_source=geeknews&utm_medium=rss&utm_campaign=news)
**Source:** geeknews | **Date:** 2026-11-20

Postgres 19 introduces a new built-in SQL command, REPACK, to remove table bloat and return disk space to the OS without relying on extensions. With CONCURRENTLY, developers can rebuild tables online while keeping reads/writes available for most of the operation, understanding the trade-offs versus VACUUM and VACUUM FULL in terms of locking and runtime impact.

**Key Points:**
- When you need to actually shrink on-disk size, consider REPACK (returns space to the OS) rather than VACUUM (makes space reusable internally); prefer REPACK CONCURRENTLY to minimize downtime.
- Because REPACK only needs a brief lock during the final file swap, schedule it during low-traffic windows and prepare a runbook to monitor lock waits and query latency.
- Use options like USING INDEX (when applicable) to control the rewrite path, and validate results by measuring table/index sizes, bloat estimates, and query performance (especially on large scans/updates) before and after.

Developers will learn how jj manages the working copy as commits without a staging area, keeps a stable logical change identity via change IDs even when commit IDs change, and allows continuing work while conflicts are recorded rather than forcing immediate resolution.

- Change how you handle conflicts: instead of stopping to resolve everything immediately, keep working with conflicts recorded in history and batch-resolve them later when it’s most convenient.

#### 4. [코드 작성을 멈추면 코드 리뷰 실력도 떨어진다](https://news.hada.io/topic?id=37534&utm_source=geeknews&utm_medium=rss&utm_campaign=news)

The article argues that relying mainly on delegation and code review—without writing code yourself—makes it hard to maintain or improve engineering expertise and review skills. The key issue isn’t the short-term quality of AI-generated code, but how skill levels diverge between engineers who still practice hands-on problem solving and those who don’t. To understand how code works and what makes it maintainable, you need direct experience designing, implementing, and debugging—not just reviewing generated output.

**Key Points:**
- Block recurring “hands-on coding time” each week (e.g., 2–4 hours) and fully deliver one small change in real production code—implement, test, and ship—to keep your instincts sharp.
- Even when using AI, adopt “I design → AI drafts”: write requirements/edge cases/test strategy first, then validate generated code with a checklist (invariants, complexity, error handling, and refactoring opportunities).
