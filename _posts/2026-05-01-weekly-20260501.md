#### 1. [Life of a Packet in Amazon EKS](https://samof76.space/life-of-a-packet-in-aws-eks.html)
**출처:** lobsters | **날짜:** 2026-05-01

이 글은 Amazon EKS에서 네트워크 패킷이 Pod 내부에서 시작해 노드의 라우팅/iptables를 거쳐 ClusterIP·NodePort, 그리고 NLB/ALB까지 전달되는 과정을 홉 단위로 추적합니다. VPC CNI가 /32 마스크, 169.254.1.1 ‘가짜’ 게이트웨이, 고정 ARP로 트래픽을 호스트 라우팅 테이블로 유도하는 원리를 이해하고, 실제 커맨드/출력으로 장애 분석과 관측(트레이싱) 방법을 익힐 수 있습니다.

**핵심 포인트:**
- Pod 네트워크 디버깅 시 VPC CNI의 ‘/32 + 169.254.1.1 게이트웨이 + ARP 고정’ 모델을 전제로 라우팅을 확인하라(예: Pod/노드에서 ip route, ip neigh로 실제 다음 홉과 ARP 항목을 점검).
- 서비스 경로 문제는 iptables 단계별로 분리해 확인하라(ClusterIP는 kube-proxy 규칙 체인, NodePort는 노드 포트 DNAT/룰 매칭을 추적; 패킷이 어느 체인에서 변환/드롭되는지 확인).
- 재현 가능한 ‘패킷 여정(runbook)’을 만들어라: 글의 부록처럼 라이브 클러스터에서 필요한 커맨드와 기대 출력(라우팅, iptables, 로드밸런서 경로)을 템플릿화해 incident 대응 시간을 줄여라.

#### 6. [이진 검색보다 빠르게 만들 수 있음](https://news.hada.io/topic?id=29069)
**출처:** geeknews | **날짜:** 2026-05-01

정렬된 배열에서 값이 존재하는지 확인하는 작업은 교과서적인 이진 검색(std::binary_search)보다 더 빠르게 만들 수 있다는 내용입니다. SIMD를 활용한 ‘SIMD Quad’ 방식은 16비트 정수 배열을 16개 원소 블록으로 나누고 블록 경계에서 4진(quad) 보간/검색을 결합해, 다양한 측정 조건에서 표준 이진 검색보다 더 좋은 성능을 보였습니다.

**핵심 포인트:**
- 데이터가 16비트 정수처럼 작고 정렬된 배열 기반 조회가 핫패스라면, std::binary_search를 고정 선택하지 말고 SIMD 기반 블록 검색(예: 16개 원소 단위) 대안을 검토/프로토타이핑하세요.
- 구현 시 ‘블록 단위 후보 축소(경계에서 더 높은 분기수의 탐색/보간)’ + ‘블록 내부는 SIMD 비교로 한 번에 필터링’처럼 계층형 접근을 설계해 분기/비교 횟수를 줄이세요.
- 벤치마크는 반드시 실제 분포(키 분포, 히트/미스 비율), 배열 크기, 캐시 적중, 컴파일러/플랫폼 SIMD(AVX2/NEON 등) 조건을 포함해 측정하고, std::binary_search 대비 유의미한 이득이 있을 때만 채택하세요.

#### 6. [이진 검색보다 빠르게 만들 수 있음](https://news.hada.io/topic?id=29069)
**Source:** geeknews | **Date:** 2026-05-01

The article explains that membership tests on sorted arrays can be made faster than textbook binary search (std::binary_search). A SIMD-based approach called “SIMD Quad” partitions a sorted uint16 array into 16-element blocks and combines quad-style interpolation/search at block boundaries, outperforming standard binary search across measured conditions.

**Key Points:**
- If you have hot-path lookups over sorted arrays of small types (e.g., 16-bit integers), don’t assume std::binary_search is optimal—prototype SIMD-friendly blocked search (e.g., 16-element blocks) alternatives.
- Design a hierarchical strategy: narrow candidates at the block level (using higher-branching search/interpolation at boundaries) and use SIMD comparisons within a block to reduce branches and total comparisons.
- Benchmark under realistic conditions—key distribution, hit/miss ratio, array size, cache behavior, and target SIMD ISA (AVX2/NEON, etc.)—and only adopt the approach when it shows a consistent, meaningful win over std::binary_search.
