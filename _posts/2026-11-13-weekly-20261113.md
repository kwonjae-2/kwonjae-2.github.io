#### 3. [Pointer Provenance in Rust vs C++](https://sofiabelen.github.io/projects/pointer-provenance-in-rust-vs-cpp/)
**출처:** lobsters | **날짜:** 2026-11-13

이 글(및 댓글)은 C++의 포인터 프로비넌스(pointer provenance) 모델이 최적화와 UB(정의되지 않은 동작)에 어떤 영향을 주는지, 그리고 Rust의 모델이 이를 어떻게 더 엄격하게 다루려는지 비교합니다. 개발자는 “주소값만 같으면 같은 포인터”라는 직관이 컴파일러 최적화에서는 깨질 수 있음을 배우고, FFI/저수준 코드에서 포인터 생성·변환 규칙을 더 보수적으로 적용해야 한다는 교훈을 얻습니다.

**핵심 포인트:**
- 정수↔포인터 캐스팅으로 포인터를 ‘재구성’하지 말고, 가능한 한 원래 포인터(또는 Rust에서는 reference/NonNull/Raw pointer)를 그대로 전달·보관해 프로비넌스를 유지하세요.
- 서로 다른 할당(객체) 사이를 포인터 산술로 넘나들거나 one-past 규칙을 어기는 접근을 피하고, 필요하면 슬라이스/범위 기반 API(예: Rust slice, C++ span)로 경계를 명시하세요.
- FFI/unsafe 구간에서는 aliasing 및 provenance 가정을 문서화하고, UB를 유발할 수 있는 패턴(포인터 재활용, 잘못된 라이프타임, 임의 주소 역참조)을 Miri/ASan/UBSan 등으로 조기 검증하세요.

#### 4. [Probabilistic data structures in Go](https://antonz.org/probabilistic-data-structures/)
**출처:** lobsters | **날짜:** 2026-11-13

이 글(및 댓글)은 Go에서 Bloom filter, HyperLogLog 같은 확률적 자료구조를 사용해 메모리/성능을 절약하면서도 “근사” 질의를 처리하는 방법과 트레이드오프(오차, false positive/negative)를 이해하는 데 도움을 줍니다. 개발자는 관측(Observability), 캐싱, 중복 제거, 대규모 카운팅/집계 같은 문제에서 언제 확률적 자료구조가 적합한지와 운영 시 주의점을 얻습니다.

**핵심 포인트:**
- 요구사항을 먼저 수치화하세요: 허용 가능한 오차율/false positive(또는 false negative) 범위와 메모리 예산을 정한 뒤, Bloom filter vs HyperLogLog 등 적합한 자료구조를 선택합니다.
- 운영 지표를 함께 설계하세요: false positive율, 추정 오차, 스케치 크기/재구성 주기 등을 메트릭으로 노출하고, 샘플링된 “정답 데이터(ground truth)”와 주기적으로 비교해 드리프트를 감지합니다.
- Go 구현은 검증된 라이브러리를 우선 사용하고, 해시/시드/병합(merge) 규칙을 표준화하세요: 동일한 해시 함수·시드·파라미터(k, m 등)를 서비스 전반에 통일해 재현성과 데이터 호환성을 보장합니다.

#### 8. [After 600 experiments, here's what I discovered about JEPA world models](https://haddyalchaer.com/jepa)
**출처:** hackernews | **날짜:** 2026-11-13

JEPA(Joint-Embedding Predictive Architecture) 기반 월드 모델을 600번의 실험으로 검증하면서, 생성(토큰 복원) 대신 ‘표현 공간에서의 예측’이 학습 안정성과 일반화에 어떤 영향을 주는지에 대한 실전 인사이트를 얻을 수 있습니다. 개발자는 JEPA를 단순한 논문 아이디어가 아니라, 데이터/학습 파이프라인과 평가 설계를 어떻게 바꿔야 성능이 나는지(특히 표현 붕괴 방지, 평가 지표, 환경 예측) 관점에서 배울 수 있습니다.

**핵심 포인트:**
- 실험 설계를 ‘재현 가능한 그리드’로 고정하세요: 데이터 전처리, 인코더/프레딕터 구조, 마스킹/예측 범위, 옵티마이저/스케줄러를 명시적으로 버전 관리하고(예: config+seed), 한 번에 한 변수만 바꾸는 방식으로 20~50런 단위의 배치를 돌려 비교하세요.
- 표현 붕괴(collapse) 감시용 지표를 기본 탑재하세요: 임베딩 분산/특이값 스펙트럼(또는 rank), 배치 간 코사인 유사도 분포, 예측-타깃 임베딩의 분산 비율 등을 로깅해 ‘잘 학습되는 척하는 실패’를 조기에 차단하세요.
- 평가를 ‘다운스트림’이 아니라 ‘월드 모델 능력’에 맞추세요: (1) 미래 상태/관측 예측 정확도(embedding-space), (2) 행동 조건부 롤아웃에서의 누적 오차, (3) 새로운 환경/시드에서의 일반화 성능을 분리 측정하고, 베이스라인(재구성 기반, 단순 dynamics 모델)과 항상 나란히 비교하세요.

#### 3. [Pointer Provenance in Rust vs C++](https://sofiabelen.github.io/projects/pointer-provenance-in-rust-vs-cpp/)
**Source:** lobsters | **Date:** 2026-11-13

This post (and its comments) contrasts C++ pointer provenance and its impact on optimizations and undefined behavior, versus Rust’s stricter approach to reasoning about pointer origins. Developers learn that the “same address means the same pointer” intuition can break under compiler optimization, and that low-level/FFI code needs more conservative rules for creating and transforming pointers.

**Key Points:**
- Avoid “reconstructing” pointers via integer↔pointer casts; preserve provenance by keeping and passing the original pointer (or in Rust, references/NonNull/raw pointers) whenever possible.
- Don’t use pointer arithmetic to cross allocation/object boundaries or violate one-past rules; prefer boundary-explicit APIs (e.g., Rust slices, C++ span) to make ranges and limits clear.
- In FFI/unsafe code, document aliasing and provenance assumptions and proactively validate with tools like Miri/ASan/UBSan to catch UB-prone patterns (pointer reuse, invalid lifetimes, arbitrary address dereference).
