#### 1. [Postgres를 Rust로 재작성, 이제 Postgres 회귀 테스트 100% 통과](https://news.hada.io/topic?id=31296)
**출처:** geeknews | **날짜:** 2026-07-10

pgrust는 PostgreSQL 18.3 호환을 목표로 Postgres를 Rust로 재작성한 프로젝트로, 46,000개 이상의 회귀 테스트 쿼리에서 Postgres의 예상 출력과 100% 일치했다고 보고합니다. 개발자는 실제 Postgres 회귀 테스트를 ‘정의된 동작(oracle)’로 삼아 호환성을 검증하는 방법과, 기존 데이터 디렉터리로 부팅 가능한 디스크 호환성 확보가 어떤 의미인지 배울 수 있습니다.

**핵심 포인트:**
- 호환성 목표를 ‘스펙 문서’가 아니라 기존 구현의 회귀 테스트/골든 출력으로 정의하고, CI에서 동일 테스트 스위트를 지속적으로 돌려 회귀를 조기에 차단하세요.
- 디스크(온-디스크 포맷) 호환이 필요하다면 ‘기존 데이터 디렉터리로 부팅’ 같은 검증 가능한 마일스톤을 잡고, 버전별 포맷/카탈로그 차이를 추적하는 체크리스트와 변환(마이그레이션) 전략을 준비하세요.
- 언어/런타임을 바꾸는 재작성에서는 안전성(Rust)만 강조하지 말고, 성능·정확성·운영성(로그/크래시 덤프/디버깅)까지 포함한 동등성 테스트(회귀·퍼징·프로퍼티 테스트)를 단계적으로 확장하세요.

#### 2. [코딩 평가에서 신호와 잡음 분리하기](https://news.hada.io/topic?id=31291)
**출처:** geeknews | **날짜:** 2026-07-10

이 글은 AI 코딩 모델의 성능을 평가할 때 ‘실제 능력(신호)’과 벤치마크/인프라 결함(잡음)을 분리하지 않으면 배포 판단과 안전성 판단이 왜곡될 수 있음을 다룹니다. OpenAI 감사에서 SWE-Bench Pro 작업의 약 30%가 깨졌을 가능성이 제기되고, 공개 작업의 통과율 변화(8개월간 23.3% 등)가 모델 향상뿐 아니라 과제 품질·검증 파이프라인의 문제일 수 있음을 시사합니다. 개발자는 평가 결과를 그대로 신뢰하기보다 재현성, 데이터/테스트의 건전성, 실패 원인 분류를 통해 평가 체계를 더 견고하게 만들 수 있습니다.

**핵심 포인트:**
- 평가 파이프라인에 ‘작업 건전성(health)’ 체크를 추가하세요: CI에서 빌드/테스트가 재현 가능하게 동작하는지, 의존성 핀ning과 실행 환경 고정(컨테이너/락파일), 타임아웃·플레이키 테스트 탐지를 기본 게이트로 두십시오.
- 실패를 원인별로 분류해 신호/잡음을 분리하세요: 모델 로직 오류, 테스트 자체 오류, 환경/의존성 문제, 명세 불명확 등으로 태깅하고, ‘깨진 과제’ 비율과 ‘모델로 해결 가능한 과제’ 비율을 별도 지표로 관리하세요.
- 벤치마크 점수를 의사결정에 바로 쓰지 말고 교차검증하세요: 동일 작업을 로컬·클린 환경에서 재실행, 샘플링 기반 수동 검토(spot check), 여러 벤치마크/내부 리포지토리 기반 평가로 일관성을 확인한 뒤 배포 기준에 반영하세요.

- 기능 동등성보다 운영지표를 우선하세요: P95/P99 지연, 에러율, 배포 빈도, MTTR 같은 SLO/SLI를 먼저 정의하고, 언어 변경 전후로 성능·비용·장애율을 계측해 ‘바꿔서 무엇이 좋아졌는지’ 측정 가능한 형태로 관리합니다.

**핵심 포인트:**

- 에러 전파/수집 정책을 명확히 하세요(첫 실패 시 전체 중단 vs 부분 성공 허용) 그리고 로깅/트레이싱에 코루틴 ID·작업 트리 정보를 포함해 동시성 디버깅 가능성을 높이세요.

#### 5. [Unified Memory, Explained: Why Mini PCs Can Run 70B Models a Big GPU Can't](https://vettedconsumer.com/unified-memory-explained-why-mini-pcs-can-run-70b-models-a-big-gpu-cant-and-where-they-slow-down/)
**출처:** hackernews | **날짜:** 2026-07-10

이 글(댓글)은 ‘통합 메모리(UMA)’가 GPU VRAM처럼 분리된 메모리보다 큰 모델 구동에 유리할 수 있다는 점을 설명하며, 왜 미니 PC(예: Apple Silicon)가 70B급 모델을 올리는데 어떤 단일 GPU는 막히는지(메모리 용량/주소공간/페이지 이동 비용) 맥락을 제공합니다. 개발자는 모델 추론에서 병목이 연산(FLOPs)뿐 아니라 ‘메모리 용량, 대역폭, 데이터 이동(PCIe)과 스와핑’이라는 사실을 이해하고, 하드웨어 선택과 배포 전략을 메모리 중심으로 재설계하는 인사이트를 얻습니다.

**핵심 포인트:**
- 배포 전 ‘가중치 메모리 예산’을 먼저 계산하세요: 파라미터 수 × (정밀도 바이트) + KV 캐시 + 런타임 오버헤드로 최소 필요 메모리를 산정하고, VRAM 단독으로 못 올리면 UMA/CPU RAM 오프로딩/멀티 GPU 샤딩 중 하나를 선택합니다.
- 데이터 이동을 줄이는 아키텍처를 우선 검토하세요: 디스크리트 GPU에서는 PCIe 왕복(호스트↔GPU)이 병목이 되기 쉬우므로, 가능하면 UMA(공유 메모리) 환경, GPU Direct/피닝 메모리, 레이어 단위 고정(상주) 전략으로 전송을 최소화합니다.
- 정밀도·컨텍스트·배치를 조절해 메모리 압력을 관리하세요: 4/8-bit 양자화, 컨텍스트 길이 제한(또는 KV 캐시 압축), 배치 크기/동시성 튜닝을 통해 ‘들어가게 만드는 것’과 ‘안정적으로 빠르게 돌리는 것’을 분리해 최적화합니다.

#### 6. [Cpp2Rust: Automatic Translation of C++ to Safe Rust](https://github.com/Cpp2Rust/cpp2rust)
**출처:** lobsters | **날짜:** 2026-07-10

Cpp2Rust는 기존 C++ 코드를 안전한 Rust로 자동 변환해, 메모리 안전성과 동시성 안전성을 강화하려는 시도와 그 한계를 다룹니다. 개발자는 어떤 C++ 패턴이 자동 변환에 잘 맞는지, 변환 후에도 어떤 검증·리팩터링이 필요한지, 그리고 FFI/빌드/테스트를 포함한 현실적인 마이그레이션 전략을 배울 수 있습니다.

**핵심 포인트:**
- 마이그레이션 대상 코드부터 선별하세요: UB 가능성(포인터 산술, 수명 불명확, 공유 가변 상태)이 높고 경계가 명확한 모듈(라이브러리/컴포넌트)을 우선 후보로 잡아 자동 변환 효율을 높이세요.
- 변환 결과를 ‘안전성 증명’으로 보지 말고 검증 파이프라인을 붙이세요: sanitizer/ASan·UBSan 기반의 기존 C++ 회귀 테스트 + Rust 측 Miri/Clippy + fuzzing으로 동작 동등성과 안전성 회귀를 동시에 확인하세요.
- 점진적 통합을 설계하세요: C ABI를 경계로 FFI 레이어를 먼저 정리하고(헤더 최소화, 데이터 구조 안정화), Rust로 옮긴 부분은 API를 좁게 유지해 호출 경로와 소유권/수명 규칙을 명확히 하세요.

#### 8. [Write code like a human will maintain it](https://unstack.io/write-code-like-a-human-will-maintain-it)
**출처:** hackernews | **날짜:** 2026-07-10

이 글은 “미래의 누군가(대개 동료나 몇 달 뒤의 나)가 유지보수할 코드”를 기준으로 코드를 작성하라고 강조합니다. 읽기 쉬운 구조, 의도가 드러나는 이름, 최소하지만 유용한 주석과 같은 습관이 버그 수정·리뷰·온보딩 비용을 크게 줄이는 핵심이라는 점을 개발자가 얻어갈 수 있습니다.

**핵심 포인트:**
- 의도를 드러내는 이름을 우선하라: 함수/변수/클래스명에 “무엇을, 왜”를 담고(예: process() 대신 calculateMonthlyInvoiceTotal), 불필요한 축약어와 맥락 없는 약칭을 피한다.
- 작게 나누고 경계를 명확히 하라: 함수는 한 가지 책임만 갖게 쪼개고, 입력/출력 계약(전제조건·반환값·에러)을 드러내며, 복잡한 조건문은 가드 클로즈/조기 반환으로 평탄화한다.
- 주석은 ‘무엇’이 아니라 ‘왜/주의점/대안’을 기록하라: 코드로 자명한 내용은 주석 대신 리팩터링하고, 비직관적 선택의 이유, 트레이드오프, 함정(성능/동시성/보안)을 짧게 남기며, 변경 시 주석도 함께 업데이트한다.

#### 1. [Postgres를 Rust로 재작성, 이제 Postgres 회귀 테스트 100% 통과](https://news.hada.io/topic?id=31296)
**Source:** geeknews | **Date:** 2026-07-10

pgrust is a Rust rewrite targeting PostgreSQL 18.3 compatibility, reportedly matching PostgreSQL’s expected outputs across 46,000+ regression test queries (100% pass). Developers can learn how to use PostgreSQL’s real regression suite as a behavioral oracle for compatibility, and what it takes to achieve on-disk compatibility that can boot from an existing PostgreSQL data directory.
