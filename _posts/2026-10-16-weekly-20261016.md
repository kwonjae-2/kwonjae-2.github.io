#### 1. [Big Fish: Exploiting a 37-Year-Old Kernel Bug in OpenBSD](https://calif.io/research/big-fish)
**출처:** lobsters | **날짜:** 2026-10-16

OpenBSD에서 37년 동안 남아 있던 커널 버그가 어떻게 실제 익스플로잇으로 이어질 수 있는지(또는 그 가능성이 어떻게 논의되는지)를 통해, 오래된 코드·가정·호환성 레이어가 보안 리스크로 변하는 과정을 배웁니다. 개발자는 “오래된 버그라도 위협 모델/환경 변화로 갑자기 위험해질 수 있다”는 점과, 커널/저수준 취약점 분석 시 어떤 관점(재현, 완화, 검증)을 가져야 하는지 얻을 수 있습니다.

**핵심 포인트:**
- 오래된 코드/호환성 경로(legacy code paths)에 대해 위협 모델을 주기적으로 갱신하고, “과거에는 안전했던 가정(메모리 배치, 권한 경계, 호출 패턴)”이 지금도 성립하는지 점검하세요.
- 취약점 이슈가 보이면 PoC 재현 환경을 최소 단위로 만들고(커널/컴파일 옵션/하드닝 설정 포함) 재현성 있는 테스트(크래시, 권한 상승 조건, 영향 범위)를 CI나 자동화 스크립트로 남기세요.
- 완화책은 ‘패치 적용’으로 끝내지 말고, 하드닝 기능(예: ASLR, W^X, stack protector, privilege separation, syscall filtering 등)이 해당 클래스의 버그를 실제로 얼마나 막는지 공격 시나리오 기반으로 검증하고 회귀 테스트를 추가하세요.

- 관측성을 기본값으로 넣으세요: tool-call마다 구조화 로깅/트레이싱을 붙이고(tracing), 재현 가능한 실행 기록(입력, 모델 설정, 도구 인자, 결과)을 남겨 디버깅과 사고 대응을 쉽게 만드세요.

#### 6. [RPKI, 이제 인터넷 경로의 70%를 보호](https://news.hada.io/topic?id=35474)
**출처:** geeknews | **날짜:** 2026-10-16

RPKI 검증을 통과하는 인터넷 라우팅 프리픽스 비율이 2025년 9월 54.0%에서 2026년 9월 70.3%로 크게 늘면서, 경로 하이재킹 같은 라우팅 사고에 대한 방어 효과가 현실적으로 강화되고 있음을 보여줍니다. 특히 ‘검증 실패(Invalid)’ 경로는 관측 지점에서 거의 전파되지(중앙값 2개) 않아, RPKI 기반 필터링이 실제 운영에서 작동하고 있음을 시사합니다.

**핵심 포인트:**
- 자사 ASN/프리픽스에 대해 ROA(Authorization)를 생성·갱신하고(리전/ISP 변경 포함), 최대 길이(maxLength) 설정을 실제 광고 정책과 일치시켜 ‘Invalid’ 발생을 예방하세요.
- 네트워크/플랫폼 관점에서 RPKI Route Origin Validation(ROV) 정책을 명확히 하세요: 기본은 Invalid 드롭, NotFound는 모니터링/점진적 정책(허용 또는 선호도 낮춤)으로 운영하며 예외 절차를 문서화하세요.
- 관측·대응 체계를 구축하세요: BGP/RPKI 상태(Valid/Invalid/NotFound)를 지속적으로 수집하고, Invalid 증가나 신규 Invalid 출현 시 자동 알림→원인(ROA 누락/AS 변경/길이 불일치) 분석→롤백/ROA 수정 런북으로 연결하세요.

#### 7. [BIPM, UTC에 윤초 추가 중단 결정](https://news.hada.io/topic?id=35472)
**출처:** geeknews | **날짜:** 2026-10-16

국제도량형총회(CGPM) 결의로 2027년 5월 20일부터 UTC에 윤초를 더 이상 삽입하지 않는 ‘연속적인 UTC’가 시행됩니다. 개발자 관점에서는 윤초로 인한 시간 역행/중복 같은 엣지 케이스가 줄어드는 대신, 장기적으로 UT1(지구 자전 기반 시각)과 UTC의 차이가 누적될 수 있어 시간 처리/동기화 전략을 재점검해야 합니다.

**핵심 포인트:**
- 애플리케이션/DB에서 ‘윤초(23:59:60)’를 전제로 한 파싱·포맷·검증 로직을 점검하고, 라이브러리/OS/NTP 스택이 윤초를 어떻게 처리(스텝/스미어/무시)하는지 문서화하세요.
- UTC 기반 타임스탬프를 단일 진실 소스로 유지하되, 천문/위성/정밀 측정처럼 UT1이 필요한 도메인은 UTC와 분리된 시간 스케일(예: UT1/TAI/GPS time)을 명시적으로 모델링하고 변환 경로를 테스트하세요.
- SRE 관점에서 시간 이상 징후(클럭 스텝, NTP offset 급변, 로그 순서 뒤바뀜)를 관측/알림 지표로 추가하고, 분산 시스템에서는 단조 시간(monotonic clock) 사용 및 ‘시간 역행 허용’ 방어 코드를 강화하세요.

#### 8. [RFC8950: Announce IPv4 with an IPv6 next-hop](https://anuragbhatia.com/post/2026/06/rfc8950-announce-ipv4-with-ipv6-next-hop/)
**출처:** hackernews | **날짜:** 2026-10-16

RFC8950은 BGP에서 IPv4 경로를 광고할 때 next-hop을 IPv6로 설정해(IPv4 NLRI + IPv6 next-hop) 듀얼스택 운용을 단순화하는 방법을 다룹니다. 개발자/운영자는 이 방식을 통해 IPv4 서비스를 유지하면서도 라우팅 인프라의 트랜스포트와 피어링을 IPv6 중심으로 전환하는 설계·마이그레이션 포인트를 얻을 수 있습니다.

**핵심 포인트:**
- IPv4 서비스는 유지하되 라우팅/피어링 세션은 IPv6로 전환하는 마이그레이션 계획을 세우고, 핵심 장비·소프트웨어(라우터/FRR/BIRD 등)가 RFC8950(또는 동등 기능)을 지원하는지 호환성 매트릭스를 먼저 작성하세요.
- 운영 자동화에 “IPv4 NLRI + IPv6 next-hop” 조합에 대한 검증 로직을 추가하세요(예: 설정 린트, 배포 전 BGP RIB/Adj-RIB-In 검사, next-hop 도달성 체크) — 단순히 IPv4 경로가 보인다고 데이터플레인이 보장되는 것은 아닙니다.
- 장애 분석/관측성 관점에서 IPv6 next-hop 기반의 포워딩을 추적할 수 있도록 텔레메트리 항목을 보강하세요(예: next-hop 해석, 재귀적 라우팅 확인, traceroute/flow 로그에 v6 next-hop 정보 포함) 그리고 롤백 시나리오(기존 IPv4 next-hop)도 함께 문서화하세요.
