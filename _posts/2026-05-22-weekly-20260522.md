#### 1. [Megalodon: Mass GitHub Repo Backdooring via CI Workflows](https://safedep.io/megalodon-mass-github-repo-backdooring-ci-workflows)
**출처:** lobsters | **날짜:** 2026-05-22

이 글은 GitHub Actions 같은 CI 워크플로가 한 번 악용되면 여러 저장소에 대규모로 백도어가 퍼질 수 있는 공격(예: 워크플로/액션 공급망 오염, 토큰 탈취, PR 기반 트리거 악용)을 개발자 관점에서 경고합니다. 개발자는 워크플로 권한·시크릿·외부 액션 사용을 최소화하고, 신뢰 경계를 명확히 하며, 감사와 모니터링으로 변조를 조기에 탐지하는 방법을 얻습니다.

**핵심 포인트:**
- GitHub Actions 권한을 최소화하세요: 워크플로에 `permissions`를 명시해 기본 권한을 줄이고(예: `contents: read`), 꼭 필요한 작업만 승격하며, 장기 PAT 대신 OIDC/단기 토큰을 우선 사용하세요.
- 외부 액션/워크플로는 핀(pin)하고 검증하세요: `uses: owner/action@v1` 대신 커밋 SHA로 고정하고, 재사용 워크플로(`workflow_call`)·서드파티 액션은 허용 목록/리뷰를 거치며, Dependabot/Renovate로 업데이트를 추적하세요.
- 시크릿 유출 경로를 차단하고 변경을 감시하세요: PR 이벤트(`pull_request_target` 등) 사용 시 체크아웃/실행 범위를 제한하고 포크 PR에 시크릿을 노출하지 않으며, 워크플로 파일 변경(특히 `.github/workflows/**`)에 CODEOWNERS/보호 규칙을 적용하고 감사 로그·알림으로 권한/워크플로 수정 이벤트를 모니터링하세요.

#### 2. [score by collisions, patch by panic](https://blog.himanshuanand.com/2026/05/score-by-collisions-patch-by-panic/)
**출처:** lobsters | **날짜:** 2026-05-22

이 글은 “모델이 망가졌다”는 불평을 넘어, 현재의 취약점/공급망 위험 환경에서 실제로 적용 가능한 방어 아키텍처를 엔지니어링 RFC 형태로 제안합니다. 개발자는 기본 거부(deny-by-default) 네트워크 정책, 영속성 차단을 위한 ephemeral 컨테이너, rootless 런타임 같은 ‘회로 차단기(circuit breaker)’를 파이프라인에 어떻게 넣고 어디서 실패할 수 있는지에 대한 관점을 얻습니다.

**핵심 포인트:**
- CI/CD와 런타임 모두에 기본 정책을 ‘아웃바운드 네트워크 egress 기본 거부’로 두고, 필요한 도메인/프로토콜만 명시적으로 allowlist로 예외 처리하라(빌드/테스트/배포 단계별로 분리).
- 영속성(persistence)과 오염된 상태를 줄이기 위해 빌드·테스트 작업을 매 실행마다 새로 생성/폐기되는 ephemeral 컨테이너(불변 이미지, 깨끗한 워크스페이스)에서 수행하고, 캐시는 읽기 전용/검증된 저장소로만 제한하라.
- 권한 상승 및 탈출 영향을 줄이기 위해 rootless 컨테이너/런타임을 기본값으로 채택하고, 필요한 경우에만 최소 권한(least privilege)으로 예외를 부여하며, 예외 경로가 ‘어디서 실패하는지’를 사전에 위협 모델링과 테이블탑 리뷰로 점검하라.

#### 3. [Google API keys keep working after you delete them long enough to be exploited](https://www.aikido.dev/blog/google-api-keys-deletion)
**출처:** lobsters | **날짜:** 2026-05-22

삭제한 Google API 키가 즉시 무효화되지 않고 한동안 계속 동작해 악용될 수 있다는 점과, ‘키 삭제=즉시 차단’이라는 가정이 위험하다는 교훈을 다룹니다. 개발자는 키 회수(revocation) 지연을 전제로 한 방어(키 교체, 제한, 모니터링, 누수 대응 절차)를 설계하는 방법을 얻을 수 있습니다.

**핵심 포인트:**
- ‘삭제’만 믿지 말고 키를 즉시 교체(rotate)하라: 유출이 의심되면 새 키 발급→배포→구 키 비활성/삭제 순으로 진행하고, 교체 기간 동안은 구 키 사용을 최소화하도록 서버/클라이언트 롤아웃을 설계하라.
- API 키에 최소 권한과 강한 제한을 걸어라: 사용 가능한 API/스코프를 좁히고(서비스별 키 분리), HTTP referrer/IP/앱 서명 등 가능한 제약을 모두 적용해 키가 살아있더라도 피해 반경을 줄여라.
- 유출 탐지 및 비용 폭주 방지 장치를 기본값으로 두어라: 요청량/오류율/과금 지표 알림, 쿼터·레이트리밋·일일 예산 한도, 이상 트래픽 자동 차단(예: WAF/프록시)을 마련하고, 키 유출 대응 런북을 준비하라.

#### 4. [Secure Boot and CA Rollover - a heads-up for distributions](https://blog.einval.com/2026/05/22#secure_boot_ca_rollover)
**출처:** lobsters | **날짜:** 2026-05-22

이 글은 Secure Boot 환경에서 인증서(CA) 롤오버가 배포판/부트 체인에 미치는 영향과, 키 교체가 잘못되면 시스템이 부팅 불가 상태가 될 수 있다는 점을 개발자 관점에서 경고합니다. 개발자는 부트로더/커널/서명 키의 신뢰 사슬이 어떻게 구성되는지, 그리고 롤오버를 안전하게 진행하기 위한 단계적 배포·검증·복구 전략의 필요성을 얻습니다.

**핵심 포인트:**
- 부트 체인의 신뢰 사슬을 문서화하고(UEFI db/dbx, shim/bootloader, 커널/모듈 서명 키), 현재 사용 중인 서명 인증서의 만료/교체 일정과 영향 범위를 릴리스 캘린더에 포함하세요.
- CA/키 롤오버는 '겹치기(Overlap) 기간'을 두고 단계적으로 배포하세요: 새 키를 먼저 신뢰 저장소에 추가→아티팩트를 새 키로 이중 서명 또는 전환→마지막에 구 키 폐기/차단(dbx 업데이트) 순으로 진행하며, 각 단계마다 실제 Secure Boot 장비에서 부팅 테스트를 자동화하세요.
- 실패 대비 복구 경로를 준비하세요: Secure Boot에서 부팅 가능한 비상 매체/리커버리 이미지, 롤백 가능한 패키지/부트로더, 사용자가 따라 할 수 있는 체크리스트(펌웨어 설정, 키 재등록, dbx 업데이트 주의사항)를 릴리스 노트에 포함하세요.

#### 6. [CODA: Rewriting Transformer Blocks as GEMM-Epilogue Programs](https://arxiv.org/abs/2605.19269)
**출처:** hackernews | **날짜:** 2026-05-22

CODA는 트랜스포머 블록을 여러 개의 개별 커널로 실행하는 대신, GEMM(행렬곱) + 에필로그(후처리)로 재구성해 연산을 더 크게 융합(fusion)하는 접근을 다룹니다. 개발자는 메모리 대역폭 병목을 줄이고 커널 런치 오버헤드를 낮추는 방식으로 추론/학습 속도를 끌어올리는 최적화 관점을 얻습니다.

**핵심 포인트:**
- 프로파일링 시 연산량(FLOPs)보다 메모리 트래픽(HBM read/write)과 커널 런치 수를 먼저 측정하고, 병목이 ‘많은 작은 커널 + 중간 텐서’인지 확인하세요.
- 가능하면 연속된 연산(예: bias/add, activation, dropout, residual, layernorm 등)을 GEMM 에필로그로 이동하거나 하나의 fused 커널로 합쳐 중간 텐서의 저장/재로딩을 제거하세요.
- 최적화 적용 전후로 정확도/수치 안정성(특히 FP16/BF16, 누적 정밀도, 정규화/softmax 주변)과 성능 지표(토큰/초, latency, GPU utilization)를 함께 회귀 테스트해 ‘빠르지만 틀린’ 변경을 막으세요.

#### 8. [Slumber a TUI HTTP Client](https://slumber.lucaspickering.me)

Slumber는 터미널에서 동작하는(TUI) HTTP 클라이언트로, curl/postman 대안처럼 요청을 빠르게 만들고 실행·비교·반복하는 워크플로를 제공한다는 점이 논의됩니다. 개발자는 API 디버깅과 테스트를 더 짧은 피드백 루프로 수행하고, 환경/인증/헤더 같은 반복 설정을 템플릿화해 생산성을 높이는 방법을 얻을 수 있습니다.

- 팀 공유를 위해 요청 정의를 레포지토리에 커밋하고(민감정보는 .env/시크릿으로 분리), CI/로컬에서 동일한 요청을 실행해 문서와 실제 동작을 동기화한다.

#### 1. [Megalodon: Mass GitHub Repo Backdooring via CI Workflows](https://safedep.io/megalodon-mass-github-repo-backdooring-ci-workflows)
**Source:** lobsters | **Date:** 2026-05-22

This piece highlights how CI workflows (e.g., GitHub Actions) can be abused to backdoor many repositories at scale—through workflow/action supply-chain tampering, token exfiltration, and trigger misuse (like PR-based events). Developers will learn practical ways to reduce blast radius by tightening workflow permissions and secrets handling, enforcing trust boundaries, and adding auditing/monitoring to detect changes early.

**Key Points:**
- Minimize GitHub Actions permissions: explicitly set `permissions` to reduce default scopes (e.g., `contents: read`), elevate only when required, and prefer OIDC/short-lived credentials over long-lived PATs.
- Pin and vet external actions/workflows: use commit SHAs instead of mutable tags like `@v1`, require review/allowlisting for reusable workflows (`workflow_call`) and third-party actions, and track updates via Dependabot/Renovate.
- Prevent secret exfiltration and monitor changes: constrain risky PR triggers (e.g., `pull_request_target`), never expose secrets to forked PRs, enforce CODEOWNERS/protection on workflow files (especially `.github/workflows/**`), and monitor audit logs/alerts for workflow and permission changes.

#### 2. [score by collisions, patch by panic](https://blog.himanshuanand.com/2026/05/score-by-collisions-patch-by-panic/)
**Source:** lobsters | **Date:** 2026-05-22

This post moves beyond complaining that “the model is broken” and presents an informal engineering RFC with concrete defensive architecture suited to today’s vulnerability and supply-chain risk landscape. Developers will learn how to apply “circuit breakers” in production pipelines—such as default-deny network egress, ephemeral containers to prevent persistence, and rootless runtimes—and where these controls may fail.

**Key Points:**
- Set a default-deny policy for outbound network egress in both CI/CD and runtime, and explicitly allowlist only the required domains/protocols (separating rules per build/test/deploy stage).
- Reduce persistence and contaminated state by running build/test jobs in ephemeral containers created and destroyed on every run (immutable images, clean workspaces), and constrain caches to read-only and/or verified stores.
- Make rootless containers/runtimes the default to limit privilege escalation and breakout impact; grant exceptions only with least privilege, and proactively threat-model and tabletop-review where the exception paths and circuit breakers can fail.

#### 3. [Google API keys keep working after you delete them long enough to be exploited](https://www.aikido.dev/blog/google-api-keys-deletion)
**Source:** lobsters | **Date:** 2026-05-22

The discussion highlights that deleted Google API keys may continue to work for a period of time—long enough to be exploited—so assuming “delete equals immediate invalidation” is risky. Developers can learn to design defenses that assume revocation delays, including key rotation, tighter restrictions, monitoring, and incident-ready leak handling.

**Key Points:**
- Don’t rely on “deletion” alone—rotate immediately: if compromise is suspected, issue a new key → deploy it → then disable/delete the old one, and design rollouts so old-key usage is minimized during the transition.
- Apply least privilege and strong key restrictions: narrow allowed APIs/scopes (separate keys per service) and enforce referrer/IP/app-signing restrictions wherever possible to reduce blast radius even if a key remains valid.
- Make leak detection and cost controls default: set alerts on request volume/error rates/billing, enforce quotas/rate limits/daily budget caps, add automated anomaly blocking (e.g., WAF/proxy), and keep a tested incident runbook for key leaks.
