#### 1. [Stop MITM on the first SSH connection, on any VPS or cloud provider](https://www.joachimschipper.nl/Stop%20MITM%20on%20the%20first%20SSH%20connection,%20on%20any%20VPS%20or%20cloud%20provider.html)
**출처:** lobsters | **날짜:** 2026-05-08

이 글(및 코멘트)은 VPS/클라우드에서 SSH로 “처음 접속할 때” 발생할 수 있는 MITM(중간자) 위험과, 단순히 TOFU(처음 본 키를 신뢰)만으로는 부족할 수 있다는 점을 다룹니다. 개발자는 인스턴스 생성 시점부터 서버 호스트키를 신뢰할 수 있는 채널로 검증·고정(pinning)해 이후 접속을 안전하게 만드는 방법들을 배웁니다.

**핵심 포인트:**
- 인스턴스 생성 직후 ‘제어면(control plane)’에서 호스트키 지문(ED25519 등)을 조회·기록하고, 로컬의 known_hosts에 ssh-keyscan/ssh-keygen -F로 사전 등록해 첫 접속을 TOFU가 아니라 검증된 키로 시작하세요.
- 가능하면 클라우드/프로비저닝 파이프라인에서 호스트키를 자동 수집해(예: Terraform/Ansible 단계) CI 비밀 저장소나 구성 저장소에 보관하고, 접속 시 UserKnownHostsFile 및 StrictHostKeyChecking=yes로 강제해 키 불일치를 즉시 차단하세요.
- 운영 절차로 호스트키 회전(재생성) 시 업데이트 경로를 마련하고, 변경 시에는 ‘왜 바뀌었는지’(재설치/재배포/침해 가능성)를 확인한 뒤 갱신하도록 runbook과 알림을 준비하세요.

#### 3. [Hackers breach JDownloader website to serve malware-laced downloads](https://www.neowin.net/news/if-you-downloaded-this-popular-software-recently-you-might-have-installed-malware/)
**출처:** hackernews | **날짜:** 2026-05-08

JDownloader 공식 웹사이트가 침해되어 정상 설치 파일 대신 악성코드가 포함된 다운로드가 배포된 사례로, 공급망(배포 채널) 보안의 중요성을 보여줍니다. 개발자는 “코드가 안전해도 배포 인프라/웹사이트가 뚫리면 사용자에게 악성 바이너리가 전달될 수 있다”는 점을 학습하고, 서명·무결성 검증·릴리스 파이프라인 보호 같은 실무 대책을 강화할 수 있습니다.

**핵심 포인트:**

- 배포/릴리스 파이프라인을 분리·강화하세요: 빌드 서버 접근 최소화(MFA, 최소권한), 비밀정보는 전용 시크릿 매니저에 보관, 아티팩트 저장소는 불변(immutable) 정책과 감사 로그를 사용하세요.
- 웹/다운로드 인프라에 탐지와 대응을 붙이세요: 파일 변조 감지(FIM), CDN/스토리지 객체 무결성 모니터링, 서명 검증 실패·비정상 트래픽 알림을 구성하고, 침해 시 신속한 회수/공지/재발급 절차(incident runbook)를 준비하세요.

#### 4. [Agents에는 더 많은 프롬프트가 아니라 제어 흐름이 필요하다](https://news.hada.io/topic?id=29296)
**출처:** geeknews | **날짜:** 2026-05-08

이 글은 복잡한 작업을 안정적으로 수행하는 AI 에이전트를 만들려면, 프롬프트를 길게 엮는 것보다 소프트웨어로 구현된 결정적 제어 흐름(상태/분기/재시도/검증)이 핵심이라고 주장합니다. "MANDATORY" 같은 강한 문구에 의존하는 프롬프팅은 한계가 있으므로, 개발자는 에이전트를 워크플로 엔진처럼 설계해 실패 가능성을 코드로 관리하는 방법을 배웁니다.

**핵심 포인트:**
- 에이전트 작업을 단계별 상태 머신/워크플로로 모델링하고, 각 단계의 입력·출력 스키마와 종료 조건(성공/실패/재시도)을 코드로 고정하세요.
- 중요 규칙은 프롬프트가 아니라 가드레일로 강제하세요: JSON 스키마 검증, 필수 필드 체크, 정책 기반 라우팅(조건 분기), 도구 호출 허용 목록/권한(캡빌리티) 제한을 적용하세요.
- 신뢰성을 위해 관측성과 복구를 내장하세요: 단계별 로그/트레이스, 실패 이유 분류, 재시도(백오프)와 보상 트랜잭션, idempotency 키로 중복 실행을 안전하게 처리하세요.
- Design agent tasks as a stepwise state machine/workflow, and hard-code each step’s input/output schema and exit criteria (success/failure/retry).
- Enforce critical rules with guardrails, not prompt wording: JSON/schema validation, required-field checks, policy-based routing (conditional branching), and tool allowlists/permissioned capabilities.
- Build in reliability via observability and recovery: per-step logs/traces, failure reason classification, retries with backoff and compensating actions, and idempotency keys to make re-runs safe.

#### 5. [From Supabase to Clerk to Better Auth](https://blog.val.town/better-auth)
**출처:** lobsters | **날짜:** 2026-05-08

이 글(댓글 스레드)은 Supabase 인증에서 Clerk로, 그리고 Better Auth 같은 대안으로 이동하는 과정에서 겪는 실무적 트레이드오프(비용, 벤더 종속, 커스터마이징, DX)를 비교·토론합니다. 개발자는 “관리형 인증 vs 직접 통제(오픈소스/자체 호스팅)” 사이에서 어떤 기준으로 선택하고, 마이그레이션 리스크를 어떻게 줄일지에 대한 판단 프레임을 얻습니다.

**핵심 포인트:**
- 인증 도입 전 체크리스트를 문서화하세요: 가격(사용자/MAU 과금), 기능(소셜 로그인·MFA·조직/팀·RBAC), 규정(데이터 위치·감사로그), 운영(가용성·레이트리밋) 항목을 기준으로 Supabase/Clerk/대안들을 비교표로 평가합니다.
- 벤더 교체 비용을 낮추려면 ‘인증 추상화 레이어’를 두세요: 앱 내부는 OIDC/JWT 표준 클레임과 내부 User/Session 모델만 의존하게 만들고, 공급자별 SDK 호출은 어댑터로 격리해 마이그레이션을 코드 변경 최소화로 처리합니다.
- 마이그레이션 계획을 단계화하세요: (1) 신규 로그인만 새 공급자에 연결 → (2) 기존 세션 병행 지원(이중 검증/토큰 교환) → (3) 사용자 계정 링크/이메일 검증 재발급 → (4) 관측 지표(로그인 성공률, 토큰 갱신 실패, 콜백 오류)를 대시보드로 모니터링하고 롤백 플랜을 준비합니다.

#### 8. [ClojureScript Gets Async/Await](https://clojurescript.org/news/2026-05-07-release)
**출처:** hackernews | **날짜:** 2026-05-08

ClojureScript에 async/await 스타일의 비동기 코드를 작성할 수 있는 방법(또는 그에 준하는 문법/매크로/라이브러리)이 논의되며, 기존 core.async(채널/고 블록)나 Promise 기반 코드와의 관계가 핵심입니다. 개발자는 비동기 흐름을 더 읽기 쉬운 형태로 표현하는 선택지를 얻고, 기존 코드베이스에서 어떤 방식으로 점진적으로 적용·혼용할지에 대한 트레이드오프(에러 처리, 취소, 디버깅, 번들/런타임 영향)를 학습합니다.

**핵심 포인트:**
- 현재 코드가 Promise 중심인지(core.async의 channel/go 중심인지) 먼저 분류하고, 경계(interop) 레이어를 명확히 하세요(예: Promise↔channel 변환 유틸을 한 곳에 모아 API를 고정).
- 에러 처리 규칙을 통일하세요: async/await 도입 시 "reject/throw"를 어디서 catch할지(함수 경계)와, 실패를 데이터로 표현할지(ex-info/Result 스타일) 팀 규약으로 정해 디버깅 비용을 줄이세요.
- 취소/타임아웃/리소스 정리를 설계에 포함하세요: 네트워크 요청, 타이머, 이벤트 리스너 등에 대해 abort/cleanup 패턴을 정하고(예: AbortController 또는 channel close), 테스트에서 타임아웃과 경쟁 조건(race)을 재현하는 헬퍼를 추가하세요.

#### 1. [Stop MITM on the first SSH connection, on any VPS or cloud provider](https://www.joachimschipper.nl/Stop%20MITM%20on%20the%20first%20SSH%20connection,%20on%20any%20VPS%20or%20cloud%20provider.html)
**Source:** lobsters | **Date:** 2026-05-08

This article (and its comments) focuses on the MITM risk on the very first SSH connection to a VPS/cloud instance and why relying on TOFU (trust on first use) can be insufficient. Developers learn practical ways to verify and pin the server host key using a trusted channel from the moment an instance is created, so subsequent SSH connections are resistant to tampering.

**Key Points:**
- Right after provisioning, retrieve and record the host key fingerprint (e.g., ED25519) via a trusted control-plane channel, then pre-populate your local known_hosts (e.g., with ssh-keyscan and verification) so the first connection is based on a validated key rather than TOFU.
- Automate host-key collection in your provisioning pipeline (e.g., Terraform/Ansible), store it in a secure config/secret store, and enforce it on clients with UserKnownHostsFile and StrictHostKeyChecking=yes so mismatches fail closed.
- Establish an operational process for host-key rotation: define a safe update path, investigate why a key changed (rebuild/redeploy vs. potential compromise), and maintain a runbook/alerts so changes are handled deliberately rather than blindly accepted.
